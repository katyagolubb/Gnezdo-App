## Интеграционные тестовые сценарии для Gnezdo

Ниже описаны **реальные пользовательские кейсы**, которые покрываются интеграционными тестами.  
Тесты выполняют **живые HTTP‑запросы** к запущенным в Docker микросервисам:

- `api_gateway` (порт 8000)
- `user-management-api`
- `book-api`

Внешние сервисы (Google Books API, Cloudinary, SMTP и т.п.) **не используются** в сценариях, чтобы не зависеть от внешней среды — мы берём только такие ветки кода, которые работают без них.

- **Обозначения ролей**:
  - **Гость** – неавторизованный пользователь.
  - **Пользователь** – авторизованный пользователь с валидным JWT.
  - **Владелец книги** – пользователь, у которого книга числится в библиотеке.

---

### Кейс 1. Регистрация пользователя и ошибка дубликата

- **Цель**: проверить успешную регистрацию пользователя и валидацию уникальности имени пользователя при повторной попытке.
- **Проверяемое взаимодействие**:
  - `api_gateway` (`/api/users/register/`)
  - `user-management-api` (`accounts.views`, `UserSerializer`, модель `User`)
  - БД PostgreSQL (создание и проверка уникальности пользователя)
- **Шаги**:
  1. Отправить `POST /api/users/register/` с уникальным `username` и валидным паролем.
  2. Повторно отправить `POST /api/users/register/` с тем же `username`, но другим email.
- **Ожидаемый результат**:
  - Первый запрос возвращает `201` и JSON с данными пользователя.
  - Второй запрос возвращает `400` и сообщение об ошибке, связанной с уже существующим `username`.

---

### Кейс 2. Получение JWT‑токена и профиля текущего пользователя

- **Цель**: убедиться, что после регистрации можно получить токен и использовать его для запроса профиля.
- **Проверяемое взаимодействие**:
  - `api_gateway` (`/api/users/token`, `/api/users/me`)
  - `user-management-api` (JWT‑аутентификация, эндпоинт профиля)
  - PostgreSQL (чтение данных пользователя)
- **Шаги**:
  1. Зарегистрировать пользователя.
  2. Отправить `POST /api/users/token` с его логином и паролем.
  3. С полученным `access`‑токеном отправить `GET /api/users/me`.
- **Ожидаемый результат**:
  - Токен успешно выдан (`200`, присутствуют `access` и `refresh`).
  - Эндпоинт `/api/users/me` возвращает профиль с тем же `username`.

---

### Кейс 3. Попытка получить список книг без авторизации

- **Цель**: проверить, что доступ к списку книг защищён и без токена возвращается ошибка.
- **Проверяемое взаимодействие**:
  - `api_gateway` (`/api/books/list`)
  - `book-api` (`UserBookListView`, пермишены DRF)
- **Шаги**:
  1. Отправить `GET /api/books/list` без заголовка `Authorization`.
- **Ожидаемый результат**:
  - Ответ `401` или `403` в зависимости от конфигурации аутентификации.

---

### Кейс 4. Добавление собственной книги и просмотр своего списка книг

- **Цель**: проверить сквозной сценарий добавления книги и отображения её в собственном списке.
- **Проверяемое взаимодействие**:
  - `api_gateway` (`/api/users/register/`, `/api/users/token`, `/api/books`, `/api/books/list`)
  - `user-management-api` (регистрация пользователя, выдача JWT)
  - `book-api` (`BookCreateView`, `UserBookListView`, модели `Book` и `UserBook`)
  - PostgreSQL (создание и чтение записей о книгах)
- **Шаги**:
  1. Зарегистрировать пользователя и получить JWT.
  2. Отправить `POST /api/books` с полями книги, используя **ручной ввод** (`name`, `author`, `overview`, `genres`, `condition`, `location`).
  3. Отправить `GET /api/books/list` с этим JWT.
- **Ожидаемый результат**:
  - Создание книги возвращает `201` и сообщение `"Book added successfully"`.
  - В списке `/api/books/list` присутствует книга с указанным названием.

---

### Кейс 5. Поиск книги по названию через API Gateway

- **Цель**: проверить интеграцию поиска книг по части названия.
- **Проверяемое взаимодействие**:
  - `api_gateway` (`/api/books/search/`)
  - `book-api` (`BookSearchView`, ORM‑запросы к `Book` и `UserBook`)
  - PostgreSQL (фильтрация по полю `name`)
- **Шаги**:
  1. Зарегистрировать пользователя, получить JWT.
  2. Добавить книгу с уникальным заголовком через `POST /api/books` (ручной ввод).
  3. Отправить `GET /api/books/search/?query=<часть_названия>` с токеном.
- **Ожидаемый результат**:
  - Запрос возвращает `200` и в списке результатов есть книга с полным уникальным названием.

---

### Кейс 6. Полный сценарий обмена: запрос и принятие

- **Цель**: проверить жизненный цикл запроса на обмен между двумя пользователями.
- **Проверяемое взаимодействие**:
  - `api_gateway`:
    - `/api/users/register/`, `/api/users/token`
    - `/api/books`, `/api/books/list`
    - `/api/exchange-requests`, `/api/exchange-requests/{id}`
  - `user-management-api` (два разных пользователя, JWT для обоих)
  - `book-api` (`ExchangeRequestView`, `ExchangeRequestDetailView`, изменение статуса `UserBook`)
  - PostgreSQL (таблицы `User`, `UserBook`, `ExchangeRequest`)
- **Шаги**:
  1. Зарегистрировать двух пользователей: владельца книги и инициатора обмена.
  2. Владелец добавляет книгу через `POST /api/books`.
  3. Владелец получает свой список `/api/books/list` и определяет `user_book_id`.
  4. Инициатор отправляет `POST /api/exchange-requests` с этим `user_book_id`.
  5. Владелец принимает запрос через `PATCH /api/exchange-requests/{id}` с `{"action": "accept"}`.
- **Ожидаемый результат**:
  - Запрос создаётся со статусом `pending`.
  - После PATCH статус меняется на `accepted`, а у книги меняется статус (например, `exchanged`).

---

### Кейс 7. Попытка запроса собственной книги

- **Цель**: проверить негативный сценарий — пользователь пытается запросить книгу, которая принадлежит ему же.
- **Проверяемое взаимодействие**:
  - `api_gateway` (`/api/books`, `/api/books/list`, `/api/exchange-requests`)
  - `book-api` (`ExchangeRequestView` с бизнес‑правилом «нельзя запросить свою книгу»)
  - `user-management-api` (JWT владельца)
  - PostgreSQL (проверка связи User ↔ UserBook)
- **Шаги**:
  1. Зарегистрировать пользователя, получить JWT.
  2. Добавить книгу.
  3. Получить свой список книг и узнать `user_book_id`.
  4. Отправить `POST /api/exchange-requests` с этим `user_book_id`, используя токен владельца.
- **Ожидаемый результат**:
  - Запрос возвращает `400` и сообщение `You cannot request your own book`.

---

### Кейс 8. Удаление книги с активным запросом на обмен без подтверждения

- **Цель**: убедиться, что при наличии активных запросов на обмен книгу нельзя удалить без явного подтверждения.
- **Проверяемое взаимодействие**:
  - `api_gateway` (`/api/books`, `/api/books/list`, `/api/exchange-requests`, `DELETE /api/books/{id}`)
  - `book-api` (`UserBookDetailView.delete`, `ExchangeRequest` с проверкой активных `pending` запросов)
  - `user-management-api` (JWT владельца и инициатора)
  - PostgreSQL (связанные записи `UserBook` и `ExchangeRequest`)
- **Шаги**:
  1. Зарегистрировать владельца и инициатора, получить два токена.
  2. Владелец создаёт книгу и получает её `user_book_id`.
  3. Инициатор создаёт запрос на обмен (статус `pending`).
  4. Владелец отправляет `DELETE /api/books/{user_book_id}` **без** параметра `?confirm=true`.
- **Ожидаемый результат**:
  - Ответ `409 Conflict`, в теле содержится информация об активных запросах (`active_requests`).

---

### Кейс 9. Обновление профиля пользователя через API Gateway

- **Цель**: проверить возможность обновления данных профиля и их последующее чтение.
- **Проверяемое взаимодействие**:
  - `api_gateway` (`/api/users/update`, `/api/users/me`)
  - `user-management-api` (`UserUpdateSerializer`, соответствующие вьюхи)
  - PostgreSQL (обновление записи пользователя)
- **Шаги**:
  1. Зарегистрировать пользователя и получить JWT.
  2. Отправить `PUT /api/users/update` с изменённым email (и/или другими полями).
  3. Отправить `GET /api/users/me` и проверить, что значения обновились.
- **Ожидаемый результат**:
  - Обновление возвращает `200`.
  - Повторный запрос профиля показывает новые значения полей.

---

### Кейс 10. Получение публичного профиля другого пользователя

- **Цель**: проверить, что один авторизованный пользователь может получить публичный профиль другого.
- **Проверяемое взаимодействие**:
  - `api_gateway` (`/api/users/{id}`)
  - `user-management-api` (`PublicUserSerializer` / соответствующий endpoint)
  - PostgreSQL (чтение другого пользователя по `id`)
- **Шаги**:
  1. Зарегистрировать двух пользователей (A и B).
  2. Получить JWT пользователя B.
  3. Отправить `GET /api/users/<id_A>` от имени пользователя B.
- **Ожидаемый результат**:
  - Ответ `200` с JSON, содержащим `username` и публичные поля пользователя A.
